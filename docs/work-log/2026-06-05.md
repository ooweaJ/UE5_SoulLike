# 2026-06-05 작업 기록

## 작업 목표

PIE 창 2개 대신 별도 프로세스로 리슨서버 1개와 클라이언트 1개를 실행해 AI/멀티플레이 동기화를 확인할 수 있는 테스트 방식을 준비한다.

## 기존 문제

- PIE 2인 테스트는 간단하지만, 에디터 내부 실행이라 백그라운드 프레임 저하나 창 포커스 문제로 화면 비교가 어려울 수 있다.
- Steam OSS 전환 전에는 NULL/직접 접속 기준으로 서버-클라이언트 동기화 문제를 먼저 분리해서 확인해야 한다.

## 구현/수정 내용

- `Scripts/LaunchNullListenTest.bat` 생성.
- 첫 번째 프로세스는 `/Game/_dev/Level/MainWorld?listen`으로 리슨서버를 실행한다.
- 두 번째 프로세스는 `127.0.0.1`로 로컬 리슨서버에 접속한다.
- 두 프로세스 모두 `UnrealEditor.exe -game` 방식으로 실행한다.
- Steam이 아니라 NULL/직접 접속 테스트가 되도록 `-nosteam` 옵션을 사용한다.

## 사용 방법

프로젝트 루트에서 다음 파일을 실행한다.

```bat
Scripts\LaunchNullListenTest.bat
```

실행 결과:

- `SoulLike Listen Server`: 리슨서버 창
- `SoulLike Client`: 로컬 클라이언트 창

## 검증 기준

- 두 창이 각각 실행되는지 확인한다.
- 클라이언트가 `127.0.0.1` 리슨서버에 접속되는지 확인한다.
- AI 타이밍 공격 몽타주 속도 변경이 서버/클라이언트 양쪽에서 같은 타이밍으로 보이는지 확인한다.

## 남은 작업

- 실제 bat 실행 후 서버/클라이언트 접속 여부 확인.
- 접속 실패 시 맵 직접 접속 방식과 GameInstance 세션 방식 중 어떤 경로가 필요한지 분리.
- NULL OSS PIE 2인 체크리스트와 별도 프로세스 체크리스트를 함께 정리.

## 백그라운드 FPS 저하 완화 및 Steam OSS 전환 준비

### 작업 목표

별도 프로세스 2개를 띄웠을 때 포커스를 잃은 창의 FPS가 크게 떨어져 동기화 비교가 어려운 문제를 완화한다.

동시에 Steam OSS 전환을 위해 세션 생성/검색 코드가 NULL과 Steam을 자동으로 구분하도록 정리한다.

### 구현/수정 내용

- `DefaultEngine.ini`의 기본 Online Subsystem을 `Steam`으로 변경했다.
- `DefaultEngine.ini` 콘솔 변수에 `t.IdleWhenNotForeground=0`, `r.VSync=0`을 추가했다.
- `Scripts/LaunchNullListenTest.bat` 실행 인자에 백그라운드 FPS 완화용 `-ExecCmds`와 `-NoVSync`를 추가했다.
- `UASGameInstance::RefreshServerList()`가 현재 OSS를 기준으로 `bIsLanQuery`를 설정하도록 변경했다.
- `UASGameInstance::CreateSession()`이 현재 OSS를 기준으로 `bIsLANMatch`와 `bUseLobbiesIfAvailable`을 설정하도록 변경했다.
- `OnJoinSessionComplete()`에서 `OpenLevel` 대신 `ClientTravel`로 세션 접속 주소에 이동하도록 변경했다.
- `Scripts/LaunchSteamMenuTest.bat` 생성.

### 테스트 방식 구분

#### NULL 직접 접속 테스트

```bat
Scripts\LaunchNullListenTest.bat
```

- `-nosteam` 사용
- 리슨서버는 `/Game/_dev/Level/MainWorld?listen`
- 클라이언트는 `127.0.0.1` 직접 접속
- 같은 PC에서 서버/클라이언트 창을 비교하기 위한 빠른 테스트

#### Steam 세션 테스트

```bat
Scripts\LaunchSteamMenuTest.bat
```

- Steam OSS 사용
- 두 창 모두 메뉴 맵에서 시작
- 첫 번째 창에서 Host, 두 번째 창에서 Refresh/Join으로 세션 확인
- 같은 PC와 같은 Steam 계정으로 2개 실행하면 실패할 수 있으므로, 실제 검증은 두 PC 또는 두 Steam 계정이 권장된다.

### 남은 위험

- `Content/_dev/Level/MainWorld.umap`가 별도 수정 상태로 남아 있으나, 이번 작업 범위가 아니므로 커밋하지 않는다.
- Steam 세션은 빌드가 성공해도 실제 Steam 클라이언트 상태, 계정, AppID 480 세션 정책에 따라 런타임 검증이 필요하다.
- 아직 `AItem`/`EquipComponent` 복제 구조가 완성되지 않았으므로, Steam 연결 이후에도 액션 동기화 버그는 별도 수정이 필요하다.

### 다음 작업

- NULL 직접 접속 bat 실행 확인.
- Steam 메뉴 테스트에서 Host/Find/Join 흐름 확인.
- `AItem`/`EquipComponent` 복제 방향 설계 및 적용.

### 검증 결과

- Unreal 5.7 `SoulLikeEditor Win64 Development` 빌드 성공.
- 첫 빌드에서 `SEARCH_PRESENCE` 매크로가 현재 include 상태에서 선언되지 않아 실패했다.
- 기존에 빌드되던 `TEXT("PRESENCESEARCH")` 키를 유지하도록 수정한 뒤 재빌드 성공.
- 실제 Steam 세션 런타임 검증은 아직 수행하지 않았다.

## 장비/아이템 복제 구조 1차 정리

### 작업 목표

플레이어와 AI가 장착한 기본 아이템을 서버 기준으로 생성하고, 클라이언트가 같은 선택 아이템을 참조할 수 있게 만든다.

현재 액션/Notify 구조는 `EquipComponent::GetCurrentItem()`에 많이 의존하므로, 선택 아이템 참조가 서버/클라이언트에서 다르면 몽타주 속도 변경, 콤보, 충돌 Notify가 서로 다른 아이템 상태를 보게 된다.

### 구현/수정 내용

- `ABaseCharacter::BeginPlay()`에서 기본 아이템을 서버 권위에서만 스폰하도록 변경했다.
- `SpawnBaseItem()`에 서버 권위, 기본 아이템 클래스, 중복 스폰 가드를 추가했다.
- `UEquipComponent::SelectItem`을 `ReplicatedUsing=OnRep_SelectItem`으로 변경했다.
- `UEquipComponent`를 기본 복제 컴포넌트로 설정했다.
- `OnRep_SelectItem()`에서 복제된 아이템의 소유 캐릭터를 보정하도록 했다.
- `AItem`을 복제 Actor로 변경했다.
- `AItem::OwnerCharacter`를 복제하고 `OnRep_OwnerCharacter()`에서 컴포넌트/Attachment 초기화를 보정하도록 했다.
- `AItem::SetupItemData()`가 한 번만 실행되도록 `bItemDataSetup` 가드를 추가했다.
- `AItem::AddActionData()`와 Attachment 생성에 최소 널 가드를 추가했다.

### 의도

- 클라이언트 로컬에서 별도 아이템을 스폰하는 구조를 줄인다.
- 서버가 스폰한 아이템 참조를 `EquipComponent`를 통해 클라이언트에 전달한다.
- Anim Notify가 `GetCurrentItem()`을 호출할 때 서버/클라이언트가 같은 아이템 Actor를 바라보는 기반을 만든다.

### 검증 결과

- 첫 빌드에서 `OnRep_SelectItem`을 넣으며 `private:` 위치가 잘못되어 포션 API가 private으로 내려가는 컴파일 오류가 발생했다.
- 접근 제어 위치를 수정한 뒤 Unreal 5.7 `SoulLikeEditor Win64 Development` 빌드 성공.

### 남은 위험

- `AItem::CurrentData`는 아직 복제되지 않는다.
- 아이템 Actor 참조는 복제되지만, 현재 액션이 무엇인지에 대한 서버 권위 액션 상태는 아직 부족하다.
- Attachment는 서버/클라이언트에서 각자 생성되는 로컬 Actor이므로, 외형/충돌 역할을 계속 분리해서 봐야 한다.

### 다음 작업

- 현재 액션 ID 또는 GameplayTag를 서버 기준으로 복제하는 최소 구조를 추가한다.
- `CurrentData` 전체 복제 대신 액션 태그/섹션/재생 속도/시작 시간 중심 구조를 검토한다.
- NULL/Steam 테스트에서 장착 아이템이 양쪽 화면에서 동일하게 보이는지 확인한다.

## 현재 액션 GameplayTag 복제 1차 적용

### 작업 목표

`AItem::CurrentData` 전체를 바로 복제하지 않고, 서버가 선택한 현재 액션의 GameplayTag를 복제해 클라이언트가 같은 DataTable에서 액션 데이터를 재구성할 수 있게 한다.

### 구현/수정 내용

- `AItem::CurrentActionTag`를 `ReplicatedUsing=OnRep_CurrentActionTag`로 추가했다.
- `GetDefaultAction`, `GetDefaultAction2`, `GetSkillAction`, `GetUltimateAction`이 공통 `SetCurrentActionByTag()`를 사용하도록 변경했다.
- `SetCurrentActionByTag()`는 GameplayTag로 `ActionTagMap`을 조회하고, 찾은 데이터를 `CurrentData`에 반영한다.
- `OnRep_CurrentActionTag()`에서 복제된 태그를 기준으로 클라이언트의 `CurrentData`를 재구성한다.
- `GetLifetimeReplicatedProps()`에 `CurrentActionTag`를 등록했다.

### 의도

- `FActionData` 전체 복제보다 작은 네트워크 상태를 사용한다.
- 서버/클라이언트가 같은 액션 태그를 기준으로 같은 DataTable 행을 바라보게 만든다.
- Anim Notify가 `GetCurrentData()`를 사용할 때 현재 액션 의미가 엇갈리는 위험을 줄인다.

### 검증 결과

- Unreal 5.7 `SoulLikeEditor Win64 Development` 빌드 성공.

### 남은 위험

- 액션 시작 시간, 몽타주 섹션, 재생 속도, 콤보 인덱스는 아직 별도 복제 상태로 정리되지 않았다.
- 클라이언트에서 Multicast 액션 실행 중 로컬로 태그를 설정하는 흐름이 남아 있으므로, 다음 단계에서 서버 권위 액션 요청/실행 구조를 더 명확히 해야 한다.
- 실제 PIE/별도 프로세스 테스트로 Notify 타이밍과 `CurrentData` 일치 여부를 확인해야 한다.

### 다음 작업

- 플레이어 기본 공격/콤보 흐름을 서버 권위 액션 요청 구조로 정리한다.
- `ABasePlayer`의 입력 RPC와 Multicast 액션 실행을 책임별로 분리한다.
- AI 이동 Notify(`ANS_MoveToTarget`)의 위치 직접 변경 구조를 검토한다.

## Grux 메테오/보스 스킬 동기화 1차 수정

### 작업 목표

Grux 보스가 소환하는 메테오와 공중 스킬 흐름에서 서버/클라이언트가 서로 다른 상태를 만들 수 있는 코드를 정리한다.

### 발견한 문제

- `AGruxMeteor`가 복제 Actor가 아니어서 서버가 스폰한 메테오가 클라이언트에 안정적으로 보인다는 보장이 없었다.
- `AGruxMeteor::OnHit()`에서 충돌 후 `Destroy()`가 권위 체크 밖에 있어 클라이언트 로컬 충돌로 먼저 사라질 수 있었다.
- `AGruxMeteor::OnTarget()`과 `Activate()`에 서버 권위 가드가 없어 타이머/투사체 활성화가 로컬에서도 실행될 여지가 있었다.
- `AGrux::OnFlySkill()`과 `AGrux::OnSkill2()`는 Anim Notify/ItemAction 경로로 서버와 클라이언트 모두에서 호출될 수 있는데, 권위 체크가 없었다.
- `AGruxItem::OnItemSkillAction()`과 `ItemAction3()`은 복제/초기화 타이밍에 `Grux` 포인터가 비어 있으면 크래시 가능성이 있었다.

### 구현/수정 내용

- `AGruxMeteor`에 `bReplicates = true`와 `SetReplicateMovement(true)`를 적용했다.
- `AGruxMeteor::Target`, `Damage`를 복제 속성으로 추가했다.
- 메테오 타이머 시작, 투사체 활성화, 충돌/데미지/파괴를 서버 권위에서만 실행하도록 변경했다.
- 충돌 이펙트는 서버에서 `NetMulticast`로 전파하도록 유지했다.
- Grux 메테오 스폰은 서버에서만 실행하고, 스폰 시 Owner/Instigator를 명시했다.
- `AGrux::OnFlySkill()`과 `AGrux::OnSkill2()`에 서버 권위 가드를 추가했다.
- `AGruxItem::OnItemSkillAction()`과 `ItemAction3()`에 `Grux` 널 가드를 추가했다.

### 의도

- 보스 스킬의 실제 상태 변화는 서버에서만 시작한다.
- 클라이언트는 복제된 메테오 Actor와 Multicast 이펙트를 관찰한다.
- 데미지와 파괴 결과가 서버 기준으로 한 번만 적용되도록 한다.

### 검증 결과

- Unreal 5.7 `SoulLikeEditor Win64 Development` 빌드 성공.

### 남은 위험

- 실제 메테오가 클라이언트 화면에서 정확히 같은 위치와 타이밍으로 보이는지는 런타임 테스트가 필요하다.
- `bFly`, `bTravel`은 복제되지만 보스 공중 이동 중 `SetActorLocation` 기반 이동은 네트워크 보정과 충돌할 수 있다.
- `ANS_MoveToTarget`와 Grux 별 모양 이동은 다음 동기화 수정 후보이다.

## 장착 아이템 표시/좌클릭 입력 회귀 수정

### 작업 목표

장착 아이템 복제 구조 1차 적용 이후 무기가 보이지 않고 좌클릭 공격이 실행되지 않는 회귀를 수정한다.

### 원인 판단

장착 아이템을 서버 스폰/복제 Actor로 바꾸면서, 클라이언트가 `EquipComponent::SelectItem`에 들어갈 아이템 Actor를 빠르게 받지 못할 수 있었다.

기존 액션 실행은 `EquipComponent::GetCurrentItem()`에 의존하므로, 클라이언트에서 선택 아이템 참조가 비어 있으면 무기 Attachment 생성과 Multicast 액션 재생이 모두 실패할 수 있다.

### 구현/수정 내용

- `AItem`을 `bAlwaysRelevant = true`로 설정해 장착 아이템 Actor가 클라이언트에 안정적으로 전달되도록 했다.
- `AItem`의 NetUpdateFrequency를 30으로 설정했다.
- `UEquipComponent::SetSelectItem()`에서 선택 아이템과 소유 Actor에 `ForceNetUpdate()`를 호출하도록 했다.
- UE 5.7 deprecation 경고를 피하기 위해 `SetNetUpdateFrequency(30.f)`를 사용했다.

### 검증 결과

- Unreal 5.7 `SoulLikeEditor Win64 Development` 빌드 성공.
- 첫 빌드에서 `NetUpdateFrequency` 직접 접근 deprecation 경고가 있었고, `SetNetUpdateFrequency()`로 수정 후 재빌드 성공.

### 남은 확인

- 에디터/별도 프로세스에서 무기 Attachment가 다시 보이는지 확인해야 한다.
- 좌클릭 기본 공격이 서버/클라이언트 양쪽에서 재생되는지 확인해야 한다.
