# 2026-06-04 작업 기록

## 작업 목표

2년 전 제작한 SoulLike 프로젝트를 AI를 활용해 어떻게 고도화할지 장기 목표를 정리한다.

단순히 "리팩터링"이라고 부르기보다, 기존 프로젝트에 투입되어 문제를 진단하고 완성도를 높이는 실무형 현대화 프로젝트로 정의한다.

## 기존 문제

- 현재 프로젝트는 `NULL` Online Subsystem 기반 로컬 멀티플레이 테스트에 머물러 있다.
- Steam OSS 전환 목표가 있지만, 먼저 게임플레이 동기화 문제를 분리해서 확인해야 한다.
- AIController가 서버에만 존재하기 때문에, AIController에서 애니메이션 속도나 정지를 제어하면 클라이언트와 동기화되지 않는다.
- 플레이어 액션, AI 액션, Anim Notify, 공격 판정, 이동 처리의 책임 분리가 명확하지 않을 수 있다.
- 2년 전 코드라 객체지향 설계, 역할 분리, 데이터 중심 액션 구조가 부족할 가능성이 있다.
- Behavior Tree와 Animation Blueprint 구조가 최신 언리얼 프로젝트 기준으로 적절한지 재검토가 필요하다.

## AI 활용 방식

- Codex와 대화하며 프로젝트 고도화 목표를 정리했다.
- 기존 문제를 네트워크, AI, 액션 구조, 아키텍처, 문서화 관점으로 분류했다.
- 장기 진행을 위해 날짜별 문서화 규칙을 `AGENTS.md`에 추가했다.
- 로드맵 문서를 작성해 앞으로의 작업 기준을 만들었다.

### 문서 구조

설치법 중심 문서가 아니라 날짜별 작업 기록 중심으로 진행한다.

이유:

### Steam OSS보다 동기화 기준을 먼저 정리

Steam OSS 전환은 중요한 목표지만, 현재는 먼저 NULL OSS 기반에서 플레이어/AI/액션 동기화 문제가 재현 가능한지 확인하는 것이 우선이다.

이유:

- Steam 전환 후 문제가 발생하면 원인이 OSS 설정인지 게임플레이 동기화인지 분리하기 어렵다.
- 액션 RPG에서는 세션 연결보다 공격, 피격, 애니메이션, 상태 동기화의 일관성이 더 핵심이다.

## 0단계 현재 상태 진단 - 1차 소스 검색

### 확인한 범위

- `Source/SoulLike/Actor/Character/Player`
- `Source/SoulLike/Actor/Character/AI`
- `Source/SoulLike/Actor/Controller/AIController`
- `Source/SoulLike/Actor/Item`
- `Source/SoulLike/Component`
- `Source/SoulLike/Notifies`
- `Source/SoulLike/ASGameInstance.cpp`
- `Config/DefaultEngine.ini`

### 1차 발견 내용

- Steam OSS 모듈과 SteamNetDriver 설정은 이미 들어가 있지만, 현재 기본 OSS는 `NULL`이다.
- 세션 생성/검색도 `bIsLANMatch = true`로 고정되어 있어 현재 구조는 로컬 LAN/PIE 검증 단계에 가깝다.
- 플레이어 입력은 서버 RPC 뒤 멀티캐스트로 몽타주 실행을 전파하는 방식이다.
- `AItem`은 `bReplicates = false`이고, `OwnerCharacter`, `Attachment`, `CurrentData` 복제도 주석 처리되어 있다.
- `EquipComponent`는 컴포넌트 복제 설정은 켜져 있지만, 선택 아이템 `SelectItem` 복제는 주석 처리되어 있다.
- `StateComponent`의 상태값은 복제되지 않는다.
- `StatusComponent`는 HP 복제가 구현되어 있어 체력 동기화만 상대적으로 분리되어 있다.
- AI 공격은 `AIController -> AIBaseCharacter -> Item -> Montage/Notify` 흐름으로 실행된다.
- `ANS_MontagePlayRate`는 Anim Notify에서 AIController를 찾아 랜덤으로 몽타주 속도 변경을 요청한다.
- `ANS_MoveToTarget`는 Anim Notify Tick에서 캐릭터 위치를 직접 `SetActorLocation`으로 보간한다.
- 공격 판정, 콤보 진행, 상태 종료는 Anim Notify가 현재 장착 아이템과 캐릭터 상태를 직접 호출하는 구조다.

### 동기화 리스크

- AIController는 서버에만 존재하므로, AIController에 의존하는 타이밍/랜덤/속도 변경은 클라이언트와 결과가 어긋날 수 있다.
- 액션의 원본 상태가 복제되는 것이 아니라 몽타주 실행 호출에 의존하기 때문에, 중간 진입 클라이언트나 지연 상황에서 현재 액션 상태를 복원하기 어렵다.
- `AItem`과 `CurrentData`가 복제되지 않으므로 Notify가 참조하는 현재 액션 데이터가 서버/클라이언트에서 다르게 해석될 여지가 있다.
- Notify Tick에서 위치를 직접 바꾸는 방식은 캐릭터 무브먼트의 네트워크 보정과 충돌할 수 있다.
- `StateComponent`가 복제되지 않으므로 Idle/Action/Hitted/Dead 같은 게임플레이 상태가 화면별로 다르게 보일 수 있다.

### 우선 수정 방향

1. NULL OSS PIE 2인 테스트에서 재현할 액션 동기화 체크리스트를 만든다.
2. 액션 실행을 `Server Request -> 서버 판정 -> 복제 가능한 Action State 갱신 -> OnRep/Multicast로 시각 표현` 흐름으로 정리한다.
3. AI 타이밍 공격은 AIController가 아니라 AI 캐릭터 또는 액션 컴포넌트에 복제 가능한 상태로 저장한다.
4. Anim Notify는 판정의 주체가 아니라 "이미 확정된 액션의 타이밍 이벤트"로 역할을 줄인다.
5. Steam OSS 전환은 위 구조가 NULL OSS에서 안정적으로 검증된 뒤 진행한다.

## 0단계 첫 안정화 작업 - StateComponent 복제 적용

### 작업 목표

플레이어와 AI가 공유하는 기본 상태값인 Idle/Action/Hitted/Evade/Dead를 서버 기준으로 클라이언트에 복제할 수 있게 만든다.

이 작업은 전체 액션 구조 리팩터링 전에 적용하는 작은 발판이다.

### 구현/수정 내용

- `UStateComponent`를 기본 복제 컴포넌트로 설정했다.
- `UStateComponent::Type`을 `Replicated` 속성으로 변경했다.
- `Type` 기본값을 `EStateType::Idle`로 명시했다.
- `GetLifetimeReplicatedProps`에서 `Type`을 `DOREPLIFETIME`으로 등록했다.
- `ABaseCharacter` 생성자에서 `State->SetIsReplicated(true)`를 명시했다.

### 의도

- 기존에는 `StateComponent` 상태가 로컬 화면마다 다르게 유지될 수 있었다.
- 앞으로 액션 실행 구조를 정리할 때 서버 권위 상태를 클라이언트가 받을 수 있는 최소 기반을 만든다.
- 아직 액션 구조 전체를 바꾼 것은 아니며, 다음 단계에서 액션 실행 요청과 몽타주 재생 흐름을 분리해야 한다.

### 검증 결과

- UE-MCP 플러그인에서 PoseSearch/StructUtils deprecation 경고가 남아 있으나, 이번 `StateComponent` 변경으로 인한 컴파일 오류는 없었다.

## AI 타이밍 공격 몽타주 속도 동기화 1차 수정

### 작업 목표

`ANS_MontagePlayRate`가 AIController에 의존해 몽타주 속도 변경을 요청하던 구조를 줄인다.

AIController는 서버에만 존재하므로, Notify에서 컨트롤러를 직접 찾아 타이밍 공격을 결정하면 클라이언트와 표시 결과가 어긋날 수 있다.

### 구현/수정 내용

- `AAIBaseCharacter`에 `TimedMontagePlayRate` 복제 상태를 추가했다.
- `TimedMontagePlayRate`를 `OnRep_TimedMontagePlayRate`로 클라이언트에 적용하도록 구성했다.
- 서버에서 속도 변경 여부를 결정하는 `TryStartTimedMontagePlayRate`를 추가했다.
- Notify 종료 시 서버 기준으로 속도를 원복하는 `EndTimedMontagePlayRate`를 추가했다.
- 실제 몽타주 속도 적용은 `MultiApplyTimedMontagePlayRate`와 `ApplyTimedMontagePlayRate`로 분리했다.
- `ANS_MontagePlayRate`는 더 이상 AIController를 직접 찾지 않고, AI 캐릭터에 속도 변경 시도만 전달한다.
- 기존 `ABaseAIController::MontagePlayRate`는 호환성을 위해 남기되, 새 AI 캐릭터 함수로 위임하도록 변경했다.
- `AItem::MontagePlayRate`에 AnimInstance와 CurrentData AnimMontage 널 가드를 추가했다.

### 의도

- AI 타이밍 공격의 랜덤 결정과 결과 상태를 서버 권위가 있는 AI 캐릭터 쪽으로 옮긴다.
- 클라이언트에는 복제 상태와 Multicast 적용으로 동일한 재생 속도 변경을 전달한다.
- Notify는 게임플레이 결정을 직접 수행하기보다 타이밍 이벤트를 전달하는 역할로 축소한다.

### 남은 위험

- `AItem`, `EquipComponent::SelectItem`, `AItem::CurrentData`는 아직 복제되지 않는다.
- 따라서 현재 액션 데이터가 모든 클라이언트에서 항상 동일하다는 보장은 아직 부족하다.
- PIE 2인 환경에서 실제 Grux/AI 공격 몽타주 속도 변경이 양쪽 화면에서 같은 타이밍으로 보이는지 확인해야 한다.

### 검증 결과

- Unreal 5.7 `SoulLikeEditor Win64 Development` 빌드 성공.
- UHT에서 `AAIBaseCharacter` 복제 속성과 `ANS_MontagePlayRate` 변경 사항이 정상 처리되었다.
- UE-MCP 플러그인/StructUtils deprecation 경고는 기존처럼 남아 있다.
