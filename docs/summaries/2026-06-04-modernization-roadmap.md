# AI 기반 레거시 언리얼 프로젝트 현대화 로드맵

## 프로젝트 정의

이 프로젝트는 2년 전에 제작한 언리얼 액션 RPG 프로젝트를 AI 에이전트와 UE-MCP를 활용해 현대화하는 작업이다.

핵심 목표는 단순 리팩터링이 아니라, 기존 코드베이스에 투입되었을 때 발생하는 문제를 AI와 함께 진단하고, 네트워크 동기화, AI 구조, 액션 시스템, 에셋 관리, 문서화까지 실제 운영 가능한 수준으로 끌어올리는 것이다.

## 최종 목표

- Steam Online Subsystem 기반 멀티플레이 환경으로 전환한다.
- 플레이어, AI, 액션, 애니메이션의 서버 권한 및 클라이언트 동기화를 정리한다.
- 기존 절차적/중복 구조를 역할 중심 객체지향 구조로 재설계한다.
- AI Behavior Tree, Animation Blueprint, Anim Notify 기반 액션 구조가 현재 프로젝트에 적합한지 재검토한다.
- AI 활용 과정과 구현 결과를 날짜별 문서로 남겨, 실무형 기존 프로젝트 투입 사례로 정리한다.

## 1. Steam Online Subsystem 전환

### 기존 문제

현재 프로젝트는 `NULL` Online Subsystem 기반 로컬 테스트에 가깝다. Steam 기반 세션 생성, 검색, 참가, 연결 흐름이 아직 프로젝트 목표에 맞게 정리되지 않았다.

### 작업 방향

- Online Subsystem 설정을 Steam 기준으로 전환한다.
- 세션 생성, 검색, 참가, 종료 흐름을 정리한다.
- 로컬 PIE 테스트와 Steam 테스트의 역할을 분리한다.
- Steam App ID, 테스트 계정, 패키징 조건을 문서화한다.

### 검증 기준

- 호스트가 Steam 세션을 생성할 수 있다.
- 클라이언트가 세션을 검색하고 참가할 수 있다.
- 접속 후 캐릭터 선택, 스폰, 이동이 정상 동작한다.
- NULL OSS와 Steam OSS 테스트 절차가 구분되어 있다.

### 산출물

- Steam OSS 설정 변경
- 세션 관련 코드/블루프린트 정리
- 날짜별 테스트 기록

## 2. 멀티플레이 동기화 문제 해결

### 기존 문제

프로젝트의 액션 RPG 구조상 이동, 공격, 피격, 스킬, 애니메이션, 상태 변화가 네트워크에서 일관되게 보여야 한다. 현재는 서버 권한과 클라이언트 표현 책임이 명확히 분리되지 않았을 가능성이 높다.

### 작업 방향

- 플레이어 입력, 서버 판정, 클라이언트 재생 구조를 분리한다.
- Replicated 변수, RPC, Multicast 사용 위치를 재검토한다.
- 액션별로 "서버가 결정하는 것"과 "클라이언트가 표현하는 것"을 문서화한다.
- 이동, 공격, 피격, 스킬을 우선순위별로 동기화한다.

### 검증 기준

- 2개 이상 클라이언트에서 같은 공격/피격 결과가 보인다.
- 서버와 클라이언트의 체력, 상태, 쿨타임이 일치한다.
- 애니메이션 시작/종료 타이밍이 크게 어긋나지 않는다.
- 지연 환경에서도 판정 주체가 명확하다.

### 산출물

- 네트워크 책임 분리 문서
- RPC/Replication 정리
- 멀티플레이 테스트 로그

## 3. AI 타이밍 공격 및 애니메이션 동기화

### 기존 문제

AIController는 서버에만 존재한다. 따라서 AIController에서 직접 애니메이션 속도를 늦추거나 정지시키는 방식은 클라이언트에 복제되지 않는다.

그 결과 서버와 클라이언트에서 서로 다른 애니메이션이 재생되거나, 서버에서만 애니메이션 정지가 발생해 AI 타이밍 공격이 동기화되지 않는 문제가 생긴다.

### 작업 방향

- AIController는 의사결정만 담당하게 한다.
- AI 캐릭터 또는 전용 액션 컴포넌트가 네트워크로 복제 가능한 상태를 관리하게 한다.
- 애니메이션 속도 변경, 정지, 재개는 복제 가능한 액션 상태로 표현한다.
- 서버 권한 액션 상태를 클라이언트 Animation Blueprint가 읽어 표현하게 한다.

### 검증 기준

- 서버와 모든 클라이언트에서 AI 공격 애니메이션 타이밍이 동일하게 보인다.
- AIController가 없는 클라이언트에서도 애니메이션 감속/정지/재개가 표현된다.
- 공격 판정 타이밍과 애니메이션 노티파이 타이밍이 일치한다.
- AI 타이밍 공격을 반복 실행해도 클라이언트 간 차이가 누적되지 않는다.

### 산출물

- AI 액션 상태 구조
- AIController 역할 축소
- 애니메이션 동기화 테스트 로그

## 4. 아키텍처 재정리와 생산성 개선

### 기존 문제

2년 전 코드라 역할 분리와 객체지향 설계가 충분하지 않을 수 있다. 캐릭터, 아이템, 액션, 노티파이, AI, UI가 서로 직접 참조하거나 중복 로직을 가질 가능성이 있다.

### 작업 방향

- 캐릭터, 아이템, 액션, 상태, 애니메이션 표현 책임을 분리한다.
- 공통 로직은 컴포넌트 또는 베이스 클래스로 이동한다.
- 직접 캐스팅과 하드코딩 경로를 줄인다.
- 생산성을 위해 반복되는 액션 정의를 데이터 중심 구조로 정리한다.

### 검증 기준

- 새 캐릭터나 새 액션 추가 시 수정 범위가 줄어든다.
- 공통 액션 흐름이 중복 구현되지 않는다.
- 빌드와 기본 플레이 테스트가 유지된다.
- 구조 변경 후 기존 플레이어 캐릭터가 깨지지 않는다.

### 산출물

- 역할별 클래스/컴포넌트 구조
- 액션 데이터 구조 개선
- 리팩터링 전후 변경 범위 기록

## 5. AI Behavior Tree와 Animation Tree 현대화

### 기존 문제

AI Behavior Tree와 Animation Blueprint가 예전 방식으로 구성되었을 가능성이 있다. 상태 전환, 공격 패턴, 애니메이션 선택 기준이 코드와 블루프린트에 흩어져 있으면 유지보수가 어렵다.

### 작업 방향

- Behavior Tree가 의사결정만 담당하는지 확인한다.
- AI 상태, 공격 패턴, 쿨타임, 타겟 추적 책임을 분리한다.
- Animation Blueprint는 복제된 상태를 기반으로 표현하게 한다.
- 필요하면 StateTree, Gameplay Tags, 데이터 에셋 기반 패턴 정의를 검토한다.

### 검증 기준

- AI 의사결정과 애니메이션 표현 책임이 분리된다.
- 공격 패턴 추가 시 Behavior Tree 전체를 크게 수정하지 않아도 된다.
- 서버/클라이언트에서 같은 AI 상태를 기반으로 애니메이션이 재생된다.
- AI 디버깅 시 현재 상태와 전환 이유를 추적할 수 있다.

### 산출물

- AI 아키텍처 진단 문서
- Behavior Tree 개선안
- Animation Blueprint 개선안

## 6. 액션 구조와 Anim Notify 사용 방식 재검토

### 기존 문제

현재 액션 구조는 Anim Notify 또는 Anim Notify State에 강하게 의존할 수 있다. 예를 들어 특정 프레임에 불덩이를 생성하거나, 이동 목표를 잡고 노티파이 스테이트 동안 이동시키는 방식이다.

이 구조가 액션 RPG에 적합할 수는 있지만, 네트워크 동기화와 서버 권한 판정이 섞이면 유지보수가 어려워질 수 있다.

### 작업 방향

- Anim Notify는 "시각적 타이밍 이벤트"와 "서버 판정 이벤트" 중 무엇을 담당하는지 구분한다.
- 공격 판정, 투사체 생성, 이동 보정, 상태 변경의 권한 주체를 정리한다.
- 액션 시작/진행/종료 구조를 데이터화할 수 있는지 검토한다.
- Notify 기반 구조를 유지할 경우 네트워크 동기화 규칙을 명확히 한다.

### 검증 기준

- 투사체 생성, 공격 판정, 이동 액션이 서버 기준으로 일관되게 동작한다.
- 클라이언트는 필요한 표현만 재생하고 최종 판정은 서버와 일치한다.
- 노티파이 누락 또는 애니메이션 재생 속도 변경에도 액션 상태가 깨지지 않는다.
- 새 스킬 추가 시 필요한 설정과 코드 수정 범위가 명확하다.

### 산출물

- 액션 시스템 진단 문서
- Anim Notify 사용 규칙
- 액션 데이터/컴포넌트 구조 개선안

## 진행 순서 제안

1. 현재 멀티플레이 구조와 액션/AI 구조를 진단한다.
2. Steam OSS 전환 전에 NULL OSS 기반 PIE 멀티플레이 검증 기준을 만든다.
3. 플레이어 액션 동기화 문제를 먼저 정리한다.
4. AI 타이밍 공격 동기화 문제를 별도 사례로 해결한다.
5. 해결 과정에서 반복되는 구조를 컴포넌트/데이터 중심으로 리팩터링한다.
6. Steam OSS로 전환하고 실제 세션 테스트를 진행한다.
7. 각 단계별로 날짜별 문서를 남기고, 마일스톤마다 요약 문서를 갱신한다.

## 현재 우선순위

1. 멀티플레이 테스트 기준 수립
2. 플레이어 액션 동기화 진단
3. AI 타이밍 공격 동기화 구조 설계
4. 액션 시스템 구조 재검토
5. Steam OSS 전환

Steam OSS 전환은 중요하지만, 네트워크 액션 구조가 정리되지 않은 상태에서 바로 전환하면 문제 원인이 OSS인지 게임플레이 동기화인지 구분하기 어렵다. 따라서 먼저 NULL OSS 기반에서 재현 가능한 동기화 테스트 기준을 만드는 것이 좋다.
