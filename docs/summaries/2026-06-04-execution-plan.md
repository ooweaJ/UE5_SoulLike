# SoulLike 현대화 실행 계획서

## 계획 목적

이 문서는 SoulLike 프로젝트를 AI 기반 레거시 언리얼 프로젝트 현대화 사례로 진행하기 위한 실행 계획서다.

로드맵 문서가 "무엇을 개선할 것인가"를 정리한다면, 이 문서는 "어떤 순서로 진행하고, 무엇을 검증하면 다음 단계로 넘어갈 것인가"를 정의한다.

## 진행 원칙

- Steam OSS 전환보다 먼저 NULL OSS 기반 동기화 문제를 재현 가능하게 만든다.
- 큰 구조 변경 전에 현재 구조를 기록한다.
- 한 번에 전체를 갈아엎지 않고, 문제를 재현한 뒤 작은 단위로 고친다.
- AI는 코드 작성뿐 아니라 구조 분석, 로그 해석, 대안 비교, 문서화에 사용한다.
- 각 단계는 작업 로그에 날짜별로 남긴다.

## 전체 단계

| 단계 | 이름 | 목표 | 완료 기준 |
| --- | --- | --- | --- |

| 1 | 멀티플레이 테스트 기준 수립 | NULL OSS PIE 기준 테스트 환경 확립 | 2인 이상 테스트 시나리오 재현 가능 |
| 2 | 플레이어 액션 동기화 정리 | 이동/공격/피격/스킬 동기화 문제 해결 | 양쪽 클라이언트에서 같은 결과 확인 |
| 3 | AI 타이밍 공격 동기화 해결 | AI 애니메이션 감속/정지/공격 타이밍 복제 | 서버/클라 AI 타이밍 일치 |
| 4 | 액션 아키텍처 재설계 | Anim Notify, 액션 데이터, 판정 책임 정리 | 새 액션 추가 기준 문서화 |
| 5 | AI/애니메이션 구조 현대화 | BT/ABP 역할 분리와 유지보수성 개선 | AI 상태와 애니메이션 표현 분리 |
| 6 | Steam OSS 전환 | Steam 세션 기반 멀티플레이 연결 | Steam 세션 생성/참가 성공 |
| 7 | 문서/포트폴리오 정리 | AI 활용 과정과 구현 결과 요약 | 제출 가능한 요약 문서 작성 |

## 0단계. 현재 상태 진단

### 목표

현재 프로젝트가 어떤 구조로 되어 있는지 파악한다. 특히 멀티플레이, AI, 액션, Anim Notify, 데이터 에셋, 블루프린트 참조 구조를 먼저 기록한다.

### 작업 항목

- C++ 클래스 구조 확인
- 플레이어 캐릭터 4종 구조 확인
- Grux/Knight AI 구조 확인
- AIController, Behavior Tree, Blackboard 역할 확인
- Anim Notify / Anim Notify State 사용 목록 확인
- 액션 데이터 에셋과 DataTable 사용 방식 확인
- 네트워크 RPC/Replication 사용 위치 검색
- 하드코딩된 에셋 경로와 직접 캐스팅 지점 목록화

### AI 활용 방식

- Codex로 소스 검색과 구조 요약을 수행한다.
- UE-MCP로 현재 레벨, 에셋, 블루프린트, Behavior Tree 정보를 확인한다.
- 빌드 로그와 에디터 로그를 요약해 위험 항목을 문서화한다.

### 산출물

- `docs/work-log/YYYY-MM-DD.md`
- 필요 시 `docs/decisions/YYYY-MM-DD-current-architecture.md`
- 현재 구조 다이어그램 초안
- 위험 목록

### 완료 기준

- 플레이어, AI, 액션, 네트워크 구조의 주요 책임을 설명할 수 있다.
- 어떤 문제가 코드 문제이고 어떤 문제가 블루프린트/에셋 문제인지 구분할 수 있다.
- 다음 단계에서 재현할 테스트 시나리오가 정해진다.

## 1단계. 멀티플레이 테스트 기준 수립

### 목표

Steam OSS 전환 전에 NULL OSS 기반 PIE 환경에서 반복 가능한 멀티플레이 테스트 기준을 만든다.

### 작업 항목

- PIE 2인 이상 실행 설정 정리
- 서버/클라이언트 로그 확인 방법 정리
- 테스트용 맵과 스폰 흐름 확인
- 플레이어 캐릭터 선택 후 접속/스폰 테스트
- 이동, 공격, 피격, 스킬, AI 전투 테스트 시나리오 작성
- 백그라운드 PIE 프레임 저하 설정 확인

### 테스트 시나리오

- 호스트 1명, 클라이언트 1명 접속
- 같은 캐릭터 선택 후 이동 동기화 확인
- 서로 다른 캐릭터 선택 후 스폰/애니메이션 확인
- 기본 공격 동기화 확인
- 피격/체력 동기화 확인
- AI 1개 배치 후 공격 타이밍 확인

### 산출물

- 멀티플레이 테스트 체크리스트
- 재현 가능한 버그 목록
- 날짜별 테스트 로그

### 완료 기준

- 같은 절차로 멀티플레이 문제를 반복 재현할 수 있다.
- 문제가 발생했을 때 서버/클라이언트 중 어디에서 어긋나는지 기록할 수 있다.

## 2단계. 플레이어 액션 동기화 정리

### 목표

플레이어의 이동, 공격, 피격, 스킬이 서버 권한 기준으로 일관되게 동작하도록 정리한다.

### 작업 항목

- 입력 처리 위치 확인
- 서버 RPC와 Multicast 사용 위치 정리
- 공격 판정 주체 확인
- 체력/상태/쿨타임 Replication 확인
- 몽타주 재생 위치와 조건 정리
- 클라이언트 예측이 필요한 부분과 필요 없는 부분 구분

### 우선순위

1. 이동
2. 기본 공격
3. 피격/체력
4. 캐릭터별 스킬
5. 상태 이상/넉백/스턴

### 완료 기준

- 2인 PIE에서 서버와 클라이언트가 같은 체력/상태를 본다.
- 공격 애니메이션과 판정 결과가 크게 어긋나지 않는다.
- 서버에서 판정한 결과가 클라이언트 표현과 충돌하지 않는다.

## 3단계. AI 타이밍 공격 동기화 해결

### 목표

AIController가 서버에만 존재하는 구조에서도 AI 공격 타이밍, 애니메이션 감속, 정지, 재개가 모든 클라이언트에서 동일하게 보이도록 만든다.

### 기존 핵심 문제

- AIController는 클라이언트에 없다.
- AIController에서 애니메이션 속도나 정지를 직접 제어하면 클라이언트에 복제되지 않는다.
- 서버와 클라이언트가 서로 다른 애니메이션 상태를 볼 수 있다.

### 작업 방향

- AIController는 의사결정만 담당한다.
- AI 캐릭터 또는 액션 컴포넌트가 복제 가능한 액션 상태를 가진다.
- 애니메이션 감속/정지/재개를 상태 값으로 표현한다.
- 클라이언트 Animation Blueprint는 복제된 상태를 읽어 표현한다.

### 작업 항목

- Grux AI 공격 흐름 분석
- Knight AI 공격 흐름 분석
- AIController에서 애니메이션을 직접 제어하는 코드 검색
- AI 액션 상태 구조 설계
- RepNotify 또는 Multicast 방식 비교
- 공격 타이밍 테스트 작성

### 완료 기준

- 서버/클라이언트 모두 같은 AI 공격 타이밍을 본다.
- AIController가 없는 클라이언트에서도 애니메이션 감속/정지가 표현된다.
- 공격 판정과 애니메이션 이벤트가 일관되게 보인다.

## 4단계. 액션 아키텍처 재설계

### 목표

Anim Notify 중심 액션 구조가 현재 프로젝트에 적합한지 검토하고, 서버 권한 판정과 클라이언트 표현 책임을 분리한다.

### 검토 대상

- Anim Notify로 투사체 생성
- Anim Notify State로 이동/추적/공격 구간 처리
- 몽타주 재생 중 공격 판정 생성
- 스킬 시전 중 이펙트/사운드/상태 변경
- 데이터 에셋 기반 액션 정의

### 작업 방향

- Notify는 타이밍 이벤트로 유지하되, 권한 있는 판정은 서버에서 처리한다.
- 시각 효과와 사운드는 클라이언트 표현 책임으로 분리한다.
- 액션 시작/진행/종료 구조를 명확히 한다.
- 액션 데이터가 캐릭터별로 중복되지 않게 정리한다.

### 완료 기준

- 새 액션을 추가할 때 필요한 데이터, 코드, 노티파이 설정이 명확하다.
- 투사체 생성과 공격 판정이 서버 기준으로 일관된다.
- 애니메이션 속도 변화나 노티파이 타이밍 차이로 액션 상태가 깨지지 않는다.

## 5단계. AI/애니메이션 구조 현대화

### 목표

Behavior Tree와 Animation Blueprint가 각각 의사결정과 표현에 집중하도록 정리한다.

### 작업 항목

- Behavior Tree 노드 역할 분석
- Blackboard 키 책임 정리
- AI 상태 전환 조건 정리
- Animation Blueprint 상태 머신 분석
- 공격 패턴과 애니메이션 선택 기준 분리
- StateTree 또는 Gameplay Tags 도입 필요성 검토

### 완료 기준

- AI의 현재 상태와 다음 행동 이유를 추적할 수 있다.
- Animation Blueprint가 서버 권한 상태를 기반으로 표현한다.
- 새 AI 패턴 추가 시 전체 구조를 크게 흔들지 않는다.

## 6단계. Steam OSS 전환

### 목표

게임플레이 동기화 기준이 잡힌 뒤 Steam OSS 기반 세션으로 전환한다.

### 작업 항목

- Steam OSS 설정 적용
- 세션 생성/검색/참가 흐름 구현 또는 정리
- Steam 테스트 조건 정리
- 패키징 테스트
- 2대 이상 환경 또는 계정 분리 테스트

### 완료 기준

- Steam 세션 생성 성공
- Steam 세션 검색 및 참가 성공
- 접속 후 캐릭터 선택/스폰/이동/기본 전투 가능
- Steam 환경에서 1~5단계에서 정리한 동기화 기준이 유지된다.

## 7단계. 문서/포트폴리오 정리

### 목표

AI를 활용한 기존 프로젝트 고도화 사례로 정리한다.

### 작업 항목

- 날짜별 작업 로그 정리
- 주요 전후 비교 작성
- AI 활용 방식 요약
- 문제 해결 사례 정리
- 회사/포트폴리오 제출용 요약 작성

### 완료 기준

- 프로젝트 목표, 문제, 해결 과정, 검증 결과를 설명할 수 있다.
- AI가 단순 코드 생성이 아니라 분석/검증/문서화에 어떻게 쓰였는지 드러난다.
- 실무의 기존 프로젝트 투입 상황과 연결할 수 있다.

## 당장 다음 작업

1. `0단계 현재 상태 진단`부터 시작한다.
2. 소스에서 RPC, Replicated, Multicast, Anim Notify, AIController 관련 코드를 검색한다.
3. Grux와 Knight의 현재 공격 흐름을 문서화한다.
4. NULL OSS PIE 2인 테스트 체크리스트를 만든다.
5. 첫 번째 재현 대상 버그를 정한다.

## 첫 번째 재현 대상 후보

가장 먼저 재현할 문제는 AI 타이밍 공격 동기화 문제로 잡는 것이 좋다.

이유:

- 기존에 실제로 겪은 문제라 재현 기준이 명확하다.
- AIController가 서버에만 있다는 네트워크 구조 문제를 잘 보여준다.
- 애니메이션, AI, 액션, 네트워크가 모두 연결된 대표 사례다.
- 이 문제를 해결하면 프로젝트의 핵심 구조 개선 방향이 자연스럽게 드러난다.
